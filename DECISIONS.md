# Decision log

One line per decision, with the reason. Used for the review walkthrough.

- **MCP SDK v2 (pinned `>=2.3,<3`)** — it is what `pip install mcp` gives today and what the brief's linked docs describe; v1 names (`FastMCP`) are legacy.
- **`uv` for Python** — one lockfile, reproducible install for the reviewer.
- **One backend package (`support_copilot`)** with sub-packages per concern — API and MCP server share models and retrieval code without path hacks, but run as separate processes.
- **Timestamps as ISO-8601 UTC strings** — SQLite has no datetime type; this format sorts chronologically as text and round-trips the fixtures exactly. No relative-date logic anywhere (fixture dates are fixed).
- **Chunking: 2 whole sentences per chunk, no overlap** — articles are 4–5 sentences, so this gives 2–3 chunks each (15 total). Sentences are never cut, so a condition or negation always stays with its claim. No overlap avoids the same article filling top-k with near-duplicates.
- **`text` vs `index_text` on chunks** — title and tags are added to the vectorised text to help recall, but only the chunk's own sentences are ever quoted as evidence.
- **Stable chunk IDs `KB-03#chunk-1`** — derived from article ID + position, so re-seeding gives the same IDs and citations stay valid.
- **FTS5 table is standalone and filled by the seed** — ticket text never changes after seeding (the only write is `reviewed_at`), so sync triggers would be dead code. Porter stemming for word variants.
- **FTS5 created with raw SQL inside the Alembic migration** — SQLAlchemy has no FTS5 construct; keeping it in the migration means one command builds the whole schema.
- **CHECK constraints on status and priority** — the DB itself rejects values outside the allowed set, not only the API.
- **Seed = migrate + delete + reload in one transaction** — repeatable by construction; `assistant_runs` is preserved.
- **`assistant_runs` stores no ticket or query text** — the brief asks to avoid logging ticket content.
- **TF-IDF: unigrams + bigrams, sublinear TF, English stop words minus negations** — bigrams reward phrases ("backup code", "background job"); sublinear TF stops a word repeated in title + tags + body from dominating; "not/no/never" are kept so "do not ask" survives as a feature.
- **Threshold 0.15, measured not guessed** — on the fixtures every correct top hit scores 0.22+, while the unscoped SFTP query's best wrong hit (KB-04) scores 0.13. 0.15 sits in that gap. Known miss: "reset my router" scores 0.21 on KB-05 via "reset"; Phase 6 eval quantifies this.
- **Category filter before threshold** — an off-category chunk is removed before scoring cut-off, as the data README asks; `top_score` is still returned so the UI can show *why* nothing passed.
- **Retrieval returns per-sentence scores inside each hit** — the composer runs in the API process and has no access to the vectoriser (it lives in the MCP server), so the server ships the scores and the composer stays pure.
- **Composer quotes whole sentences verbatim, never rewrites** — cutting a sentence can drop its condition ("if no transaction exists … may retry once"). Tests assert every quoted line is an exact sentence of a retrieved chunk.
- **Score picks which sentences, article order picks their sequence** — so KB-01's "if pending, do not ask for another payment" is always read before "may retry once".
- **Disclaimer rule** — a sentence matching "does not define/cover/…" is never quoted; if it is the *best* match, the result is `insufficient_evidence`. This is what passes the bank-decline-fee case, where KB-06 scores 0.22 (above threshold) only because it says it does *not* cover the topic.
- **`insufficient_evidence` is a state with a reason and zero citations** — never an empty string, never a partial answer.
- **"Facts to confirm" are mined from retrieved KB sentences (check/confirm/collect/record…), not a hand-written checklist** — keeps the summary grounded and cited; a checklist would be uncited knowledge.
- **FTS query: alphanumeric words only, each quoted, OR-joined, stop words dropped** — raw text breaks MATCH syntax; default AND returns nothing for a sentence. bm25 ranks.
- **bm25 floor of 2.0 for similar tickets** — OR-matching returns any ticket sharing one common word; on the fixtures real matches score 4.2+ and noise 1.6 or less. Calibrated on 12 tickets, so it is a documented knob, not a universal constant.
- **`TicketFilter` uses Literal enums** — invalid values fail validation before any SQL is built; column names come from the model's own field names, values are bound parameters.
- **No synonym map (MFA vs "multi-factor authentication")** — left as a documented limitation of sparse retrieval; ticket titles happen to carry the shared word "authenticator".
- **Injection defence is structural** — ticket/article text is only ever interpolated into quoted output; no code path parses it for actions, so there is nothing for an injected instruction to steer.
- **MCP server returns evidence only; composer stays in the API** — matches the brief's wording and means the server process cannot produce answer text at all.
- **`build_server(db)` factory, tools as closures** — engine and TF-IDF index are built once at startup and tests run the same server in-process via `Client(server)` with no module-level state.
- **Read-only at two layers: `file:…?mode=ro` URI and `PRAGMA query_only = ON`** — independent guards; a test proves UPDATE/DELETE/CREATE fail and that a missing DB file is not created.
- **Unknown ticket ID → typed `found=false`, not a tool error** — not-found is a normal outcome the API maps to 404; `is_error` is kept for bad input and real failures (422/503). Resources have no typed channel, so an unknown ID there raises.
- **Input bounds in the tool signature (query 1–500 chars, `top_k`/`limit` 1–10, ID patterns, enum categories)** — the SDK rejects bad input before our code runs, and the bounds appear in the tool schema.
- **`search_knowledge` does not expose the threshold** — a caller cannot lower the evidence bar; it is reported in the result instead.
- **`NullPool` + one connection per tool call** — no connection is shared across threads if the SDK runs sync tools in a worker; cost is negligible for SQLite.
- **Tools carry read-only annotations (`read_only_hint`, not destructive, idempotent, closed-world)** — the SDK default advertises tools as possibly destructive, which the Inspector showed; hints are metadata only, the read-only connection remains the guarantee.
- **One MCP stdio session opened in the FastAPI lifespan (`McpGateway`)** — the stdio client uses anyio task groups and must be entered and exited by the same task; per-request sessions would also pay a process start each call.
- **MCP failure is fail-fast 503, no restart-and-retry** — a restart would have to run inside the lifespan task, and a silent retry can hide a crashing server; `/health` reports `mcp_ready=false` and ticket routes keep working.
- **App still starts if the MCP server cannot start** — the queue stays usable and the failure is visible in `/health` instead of a boot crash.
- **10 s read timeout on MCP calls** — a hung server becomes a 503, not a hung request.
- **Readiness check is a real `list_tools` round trip** — protocol `ping` is removed in SDK v2 (2026-07-28 spec), and a cached flag would not notice a dead process.
- **One fixed flow per action in a dict keyed by the `Action` enum** — ticket and article text only travels as tool arguments or quoted evidence, so it cannot select a tool.
- **Per-action required fields checked in a model validator; `extra="forbid"` on the request and on `TicketFilter`** — bad or unknown input is a 422 before any tool runs, rather than being ignored.
- **Query limit 500 chars** — same bound as the MCP tools, so the API never forwards something the server would reject.
- **API re-validates MCP results into the shared pydantic models** — a contract drift between server and API fails loudly instead of producing a malformed answer.
- **Ticket list/detail/reviewed use SQLAlchemy directly, not MCP** — the MCP server is read-only by design; the only write (reviewed) and the run log belong to the API.
- **Run record written in `finally`, metadata only** — every validated request is logged, success or failure, without storing query or ticket text. Requests rejected with 422 never reach the handler and are not recorded.
- **`top_k` fixed at 3 in the API and passed explicitly** — the retrieval metadata in the response is then what was actually asked for.
- **Frontend is hand-written Vite + React + TS, no UI or data-fetching library** — three panels and four endpoints; a small `useLoad` hook covers loading/error/ready and drops stale responses.
- **Vite dev proxy for `/api` and `/health` instead of CORS** — the browser only talks to one origin, so the API needs no CORS policy to get wrong.
- **The form does not duplicate request rules; the server's 422 message is shown as the validation error** — one source of truth (`AssistantRequest`), and the validation state is real, not simulated.
- **`Citation` gained optional `score` and `excerpt`** — the UI must show a score and an expandable passage per citation, and both already existed in the evidence; nothing new is computed.
- **Answer is cleared when the ticket or action changes; draft editor is keyed by `run_id`** — a draft for one ticket can never sit next to another ticket, and a new run replaces old edits.
- **No send button exists; the draft carries a permanent "Draft — not sent" label and only a Copy action** — the brief's boundary is enforced by absence, not by a disabled control.
- **System fonts and no CDN assets** — the UI must render with the network off.
- **Threshold 0.15 → 0.17** — the sweep showed 0.15 sat 0.0001 under a wrong match ("How do I reset MFA?" → KB-05 at 0.1501). On the labelled set the best wrong match is 0.150 and the weakest right one 0.182; 0.17 is the middle of that gap. Cost: that query is now refused instead of answered from the wrong article.
- **Sweep scores the real path (scope + composer), with four outcomes** — a retrieval-only sweep would count the bank-decline case as an accept although the composer refuses it; "wrong source" is kept apart from "false accept" because citing an off-topic article is the worst outcome.
- **Ranking metrics are measured unscoped** — with one or two articles per category a scoped ranking is always right and would flatter the numbers.
- **BM25 baseline is an in-memory FTS5 table inside the eval only** — compares methods on identical chunk text without adding a second index to the product. Result: a tie on 7 articles, which is itself the finding.
- **Unseen query words count against the score (`_coverage`)** — sklearn drops out-of-vocabulary words, so a short out-of-scope question with one matching word ("change") scored 0.20, above real hits. The query's length now includes unseen words. Result: false accepts 1 → 0. Cost: the "big spreadsheet" paraphrase (0.18 → 0.166) is now refused. T-103's draft is also refused (0.144; already under 0.17 at 0.169), which is right: the ticket is a missing receipt email and the only checkout-scoped match is the payment-timeout article.
- **Unseen words weighted at the smallest indexed idf, not the largest** — the "found in no chunk" weight is the textbook choice but dropped T-104's own draft to 0.127, because ticket text is full of ordinary words seven articles never use. The mild weight keeps T-104 at 0.197 and still puts the false accept at 0.13.
- **Grounding checker compares answers with the database, not with the answer's own citations** — otherwise a composer bug would vouch for itself. Non-quote lines must be on a fixed template allowlist, so adding a factual sentence to the composer fails the suite.
- **Tamper tests for the checker** — added claim, shortened sentence, wrong chunk tag, fabricated citation; a checker that never fails proves nothing.
